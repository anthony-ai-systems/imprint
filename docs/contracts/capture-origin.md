# Capture origin

Automated callers set the process environment variable IMPRINT_CAPTURE_ORIGIN=automation before starting the host CLI. The hook bridge preserves it. Stop capture returns a content-free machine_origin skip before opening an operator store, even if an event supplies operator_text or claims human origin. Unknown nonempty transport markers also skip as unverified. This is a cooperative provenance contract, not authentication against a malicious local caller.

Without a machine marker, transcript origin.kind=human is explicit human authorship. The host interactive prompt sources typed, queued and suggestion_accepted are accepted when origin is absent. SDK and unknown prompt sources with no explicit human origin return unverified_provenance and cannot create operator canon. Headless human submission remains supported with explicit human transcript origin, or the existing direct operator_text hook API from a human caller. Do not set an automation marker for that human submission.

Human text quoting automation is still human: text does not establish transport identity. Existing structural checks and legacy diagnostic markers remain; a malformed complete transcript line still fails closed, which means nothing is read from that transcript. Both normal and bounded-tail transcript parsers apply the same gate. Existing canon is not relabeled or deleted.

Known automated producers: the Astra–Fable peer wrapper and Fully Aware daily scan, nightly fix, and taste distiller. Deploy producer markers and this capture gate together; older installed Imprint versions ignore the environment marker. Roll back them together if necessary.

## T3 threads

T3 submits every prompt through the SDK, so its transcript entries carry `entrypoint=sdk-ts` and `promptSource=sdk` whether a person or an agent wrote them. They stay unverified by default.

With `t3_capture_origin: true`, an unverified `sdk-ts` entry from a run with `T3CODE_THREAD_ID` set is checked against T3's own records, read-only, from `<T3CODE_HOME or ~/.t3>/userdata/statev2.sqlite`. T3's command line reports authorship per thread, not per message, so those records are the only per-message source today. The entry counts as human only when all of these hold:

- **Session.** A row in `orchestration_v2_projection_provider_threads` for that thread has `nativeThreadRef.nativeId` equal to the Stop event's `session_id`, compared as an exact string. Every job an agent starts inherits `T3CODE_THREAD_ID`, so without this a nested run could match a person's words. No such row, a missing field or any other shape leaves the entry unverified, with the reason below.
- **Newest match.** Among the thread's newest 64 prompts, the newest with the same words decides, so an agent repeating a person's words is judged as the agent.
- **Author.** That prompt has `createdBy=user`, a string `creationSource` of `web` or `mobile`, and a message id.
- **Not a machine or a third party.** It has no truthy `senderThreadId`, `notification`, `scheduledTaskId` or `context.guest`, and a `context` of any other shape refuses it. Scheduled and webhook prompts keep `user` and `web`; so does a message sent for a guest.
- **Not a plan.** Its text does not begin with `PLEASE IMPLEMENT THIS PLAN:\n`, after removing one leading `Ultrathink:\n`. T3's Implement button sends the assistant's plan that way and no field marks it.

"The same words" is compared after removing, from both sides, leading `<system-reminder>` and `<task-notification>` blocks, one `Ultrathink:\n` prefix, `<pasted_content>` and `<t3_context>` blocks, and attachment lines. A stored context chip `[label](t3-context://v1/kind/id)`, with `!` before an image, is compared in the form T3 sends the provider, `[Kind: label; ref=id]`. A line T3 adds for an image or file, its note that a captured window was cut, and its captured-window data block are removed from both sides as well, so an image sent with that data still matches. An entry that holds the context of a handoff, then `\n\nUser message:\n`, then the operator's words matches on the text after the last such marker, and only when the whole entry matches nothing, so an agent that sends text containing the marker is still judged as the agent. Only those words are stored. Inside one session the match is still by words, because T3 gives the provider a random prompt id rather than the message id. A prompt T3 sends in any other form stays unverified and is counted as `t3_prompt_unmatched`. That includes a `$name` skill mention, which T3 rewrites and Imprint cannot map back without knowing the skill list.

The record settles only what the entry left unverified. A declared origin, a structural refusal and `IMPRINT_CAPTURE_ORIGIN=automation` all stand. A capture whose verdict basis is `host_record`, and no other, carries an `org.imprint.host_origin` extension with `host`, `basis`, `message_id`, `created_by` and `creation_source`. The parsers return the basis, so a turn decided by its own origin or prompt source is never stamped.

Both parsers use only the newest prompt. An unverified prompt newer than the last operator entry ends the search and returns the unverified skip, so an older turn is not read again once its capture mark has expired. A tool result is not a prompt and does not end the search. If a person's prompt and an agent's both arrive before any Stop, the person's turn is skipped.

A prompt sent while a turn runs reaches the transcript as a `queued_command` attachment with no entrypoint. Where a host record can judge it, it is read as a prompt, one whose T3 record is checked as for an `sdk-ts` entry, and its own machine origin, meta flag or forwarded intent still keeps it out. Without a host record it is passed over, because it could only be unverified and would hide the turn it interrupted. The newest-prompt rule still applies, so an opening correction followed by a steer that is not feedback is not captured.

A turn the capture marks can no longer answer for is not read again. Marks are swept after 30 days, so an operator turn older than that returns `operator_turn_expired`; a turn with no readable time is left to the marks. A Stop event with no session id gets a new session each time, so its marks are kept against the transcript path instead.

A T3 record that cannot be read is not evidence about the prompt. A missing store, a missing table or column, a locked store, a stored payload that is not valid JSON, or a message payload that is not an object all leave the entry unverified. So does a T3 home that cannot be resolved, or a newer row with no string text. The Stop receipt then gives `t3_record_unavailable` instead of `unverified_provenance`, the skip is logged to `logs/capture-skips.jsonl`, and `imprint health` reports `t3_record_unavailable` as a degraded reason for 24 hours, with `t3_record_unavailable_24h` and `t3_record_unavailable_newest_age_seconds` counted from the newest 64 KiB of that log. The turn itself is not retried.

A record that decodes but cannot judge the prompt is logged the same way under its own reason, and each is counted in `capture_skips_24h`. These counts are of Stop events, not lost turns, so a session that keeps hitting one skip adds a line per Stop. The log keeps one older copy, `capture-skips.1.jsonl`, once it passes 4 MiB, and health reads only the current file:

- `t3_session_ref_unreadable`: the thread has provider rows and none names any session. That is a change in T3's shape, so it is also a degraded reason.
- `t3_session_unmatched`: no row names this session. A nested run that inherits the thread reaches this in normal use, so it does not degrade health.
- `t3_prompt_unmatched`: the session matches and no recent prompt has these words, again a normal result for a nested run.
- `t3_scratch_thread`: T3 keeps the thread in its home's `scratch` folder, which is where its "No project" chats live. No prompt in one is credited, a person's included, and this does not degrade health. The same reason covers a thread whose folder cannot be read.

The scratch rule exists because `creationSource` names the client, not the person. A script that drives the T3 app is recorded as `user` and `web`, the same as a person typing, and no field separates them. So a script typing into a chat in a project is still credited until T3 can mark it. A thread's folders are `worktreePath` on its T3 thread row and the root of its T3 project, and either one in `scratch` is enough. Both are compared after following symlinks. A path that is not absolute or cannot be read counts as scratch, as does a session whose thread has no row or no folder. A row that is not an object counts as an unreadable record. A run naming a thread this store does not hold stays `t3_session_unmatched`.

A prompt T3 does record and that a check above refuses is a judgment, so it stays an ordinary `unverified_provenance` and is not logged.

Someone else's words are kept out of the stored text where they can be told apart. On every host, leading `<system-reminder>` and `<task-notification>` blocks, `<pasted_content>` and `<t3_context>` blocks, T3's captured-window data, lines that are one attachment bracket and nothing else, `>` block quotes, and text between two runs of four or more equals signs are removed before the words are stored. So is the text after a lone run that a colon introduces, up to the end of the message. Any other lone run is a heading underline or a divider and hides nothing. A message with nothing left is skipped as `not_explicit_feedback`. For a capture attested by T3, the `Ultrathink:\n` prefix is removed as well; on other hosts it is only ignored by detection, because it could be the operator's own line.

A paste block ends at the closer with its own `id`, however much sits inside it, then at the closer that pairs with it, so a tag quoted in the paste does not end the paste early. Attributes of any length are read. An opener with no closer runs to the end of the message when it has an `id` or starts a line. A bare tag in the middle of a sentence with no closer is the operator talking about the tag, and it stays. A paste with no `id` still ends at its first closer, so the text after a stray close tag inside one reads as the operator's, and so does a close tag with no opener.

Two T3 forms keep part of what they hold. A context chip's `[Kind: label; ref=id]` marker is stored as its label, so "Do not change" keeps its object, and the marker and label are blank for detection, so a chip named after a correction does not fire by itself. An assistant quote link `[Assistant quote](t3-citation://v1/...)` carries the assistant's words: only the operator's comment on it is kept, on its own lines, and it is read as the operator's reply. A malformed link stays as text.

Detection reads the same message with those spans still marked, and a blanked span sits like a sentence boundary, so a line after a removed quote is the operator's reply, while a line a colon introduces, even across a blank line, is what the colon reported. It also ignores one leading `Ultrathink:\n` on every host, and these spans, which stay in the stored text: a quotation in double or curly quotes, one line or several lines of a paragraph; a single-quoted phrase; a code fence, where an unclosed fence runs to the end of the message; and a `---` block, between two lines of dashes or from a lone line of dashes that a colon introduces. A quotation is part of its sentence, and a fence or a `---` block is as often the operator's own. Text with none of these marks counts as the operator's words.

Rules that read a statement (`approval`, `standard` and `direct`) skip a match in a sentence that ends in a question mark, so an ordinary question such as "Is that right?" is not a verdict. A reply that opens with `no` to a question is not told apart from a correction: "No, I said X" and "No, I have not seen that" read the same.

A compact retrieval line is the stored text unchanged when it fits. Otherwise it is every sentence of the operator's that reads as feedback, in document order, each sliced from the stored text and read with the same spans and every host block masked, or else the opening of the words left once those spans are removed. Both keep the message's last sentence where it fits, whether or not it reads as feedback, because the end of a message is where it overrules what came before it. Sentences fill backward from the last, so the last always survives, cut if it needs more than half the 400 bytes. A sentence ends at `.`, `!` or `?` and at a line break, but not at a common abbreviation or at a line that goes on in lower case. A line is never empty: a record that is nothing but quoted text keeps its own opening. Choosing a sentence from a record already captured is wider than detection: it also takes a sentence that opens with a contrast or an edit, or says something is wrong, none of which capture a message by themselves.

A transcript that does not exist, is empty, or disappears during the read at Stop is skipped as `transcript_unavailable` and logged to `logs/capture-skips.jsonl`, because blocking the stop cannot make the host write it. A symlink or other non-regular file, or a path that cannot name a file, is still refused, and nothing is read from it, but a blocked stop cannot repair it, so it returns `transcript_refused`, exit 0. A malformed complete line or text that is not UTF-8 is handled the same way and returns `transcript_malformed`, so a bad line and a bad file count apart. Each skip is logged, counted in `capture_skips_24h` and reported by `imprint health` as a degraded reason, which replaces the hook failure it used to leave. Only a file still changing can heal, so a file replaced during the read, or a final line not yet complete, still blocks the stop once.

Those two skips say why in the same log line, which never holds a path:

- `code`: what turned the transcript away. For `transcript_refused`, one of the four checks that share the message `transcript_path must be an absolute regular non-symlink file`: `path_not_absolute`, `path_stat_failed`, `path_not_regular` or `path_open_failed`. For `transcript_malformed`, `malformed_line` or `not_utf8`. These names are stable. Any other refusal reads `unclassified`.
- `errno`: the system error's name, such as `EACCES`, where there is one. An errno with no name on this platform is given as its number.
- `path_class`, on `transcript_refused` only: the kind of file for `path_not_regular` (`symlink`, `directory`, `fifo`, `socket`, `block_device`, `char_device` or `other`), otherwise the form of the value (`empty`, `relative`, `absolute`, `home_relative` or `null_byte`).
- `path_hash`: 16 hex characters of an HMAC of the path, keyed with this installation's `session-map.key`. Equal hashes are one file, so a repeat can be told from many files failing once, and a guessed path cannot be checked against the log.

The same holds for input a retry cannot change. A Stop event that is not a JSON object, or is too deep to read, fails open as `hook_input_invalid`. A path that cannot name a file is refused. An unreadable config is a capture failure, not such an input: every capture would be lost until someone repairs it, so it blocks the stop once, and only once, to be seen.

Blank transcript lines are skipped by both parsers. So is a line of valid JSON too deep or too long to read, which says nothing about the turn. A lone surrogate in a transcript or a Stop event is replaced with `?`, on the transcript side and the T3 side alike, before anything is stored or compared.

A transcript up to 16 MiB is read whole. Over that, the last 2 MiB are read, then the last 16 MiB once if they hold no prompt. A correction further back than that is lost, and the turn is skipped as `transcript_tail_exhausted`, logged and counted in `capture_skips_24h`, rather than as a missing prompt.

The prior assistant message is kept as context up to 64 KiB. Past that it is cut, and the capture and its receipt record `context_truncated` in `org.imprint.transcript`. Operator text is never cut: stored text over 256 KiB that reads as feedback is skipped as `operator_text_oversized` and logged to `logs/capture-skips.jsonl`, because blocking the stop cannot make it shorter.

## T3 homes

Hooks run only in a Claude home that registers them, and a home with hooks can send them to another store. Neither shows anywhere, because a home that never runs a hook writes nothing. With `t3_capture_origin: true`, `imprint health` reads the homes from T3's own `<T3CODE_HOME or ~/.t3>/userdata/settings.json`, read-only, then each home's `settings.json`, and adds a `t3_homes` metric. With it off, neither file is read and the metric is absent. This adds no setting.

`t3_homes.state` is `read`, `settings_missing` or `settings_unreadable`. A file that cannot be read, or instances T3 itself would refuse, leave `homes` empty and health carries on. Each row in `homes` holds no path and no value of any setting:

- `instances`: the T3 instance ids on this home. Paths that resolve to one folder are one home, and T3's default instance is included when its file leaves it out. A home with no `homePath` is `CLAUDE_CONFIG_DIR` from the instance's environment, or else `~/.claude`.
- `enabled`: whether any of those instances can run.
- `hooks`: `complete`, `partial`, `none` or `unreadable`, counted by Imprint's ownership marker in `SessionStart`, `UserPromptSubmit` and `Stop`. A home with no settings file has `none`. A file or home path that cannot be read is `unreadable`, not `none`.
- `data_root`: `same`, `different` or `unknown`, from resolving the config and data root a hook would use with the instance's `environment` and then the home's `env` applied, and comparing the operator folder with this one. A home that sets none of the variables involved is `same`. A config that cannot be read is `unknown`. If instances on one home disagree, `different` wins.

Three counts sum these up, for enabled homes only: `homes_missing_hooks` is `none` or `partial`, `homes_different_data_root` is `different`, and `homes_unreadable` is hooks `unreadable` or a data root `unknown`. A disabled instance is listed and not counted, because it launches nothing, unless a project turns it on, because T3 then runs it there.

These are reports. They change neither `status` nor `degraded_reasons`, so a home that is waiting for hooks does not hold health at `degraded`. Reading the data root stops at those two places: a variable set on the T3 server's own process, or in front of a hook's command, is not seen.

## Scratch chats and Jev

T3's scratch chats get no Jev. With `t3_capture_origin: true`, the prompt hook and `imprint retrieve --prompt` send no request, in `jev` or `shadow` mode, from a thread T3's records place in its scratch folder. The turn gets the deterministic answer, with `selector_method` `deterministic` and `selector_outcome` `t3_scratch_thread`, and no line in the decision log. Session start is unchanged, and it never calls Jev.

The same records are read the other way round from capture. Capture credits nothing it cannot place, because crediting is the risk. Here the risk is losing Jev, so a thread the records cannot place keeps it: a missing or locked store, a missing table, a payload that cannot be read, no thread row, no folder, and a folder that is not absolute or cannot be read all leave the turn as it was. Only a folder that resolves into `scratch` counts, and either of the thread's two folders is enough, even if the other cannot be read.

A provider row must still name this session, because every run inherits `T3CODE_THREAD_ID`. The prompt hook uses the event's `session_id`. `imprint retrieve` uses `CLAUDE_CODE_SESSION_ID`, which Claude Code sets for what a session runs, and otherwise its `--session` value, which can be any label. So a nested run has its own session and keeps Jev even inside a scratch thread, and a `retrieve` run with neither variable set and a label T3 does not know keeps it too.

T3 is read only on a turn that would call Jev, with the setting on and `T3CODE_THREAD_ID` set, and then only the thread row, its project's root and its provider rows, never a prompt. With the setting off nothing changes and T3's store is not opened. The check takes about 0.2 ms on a 60 MB store and adds no measurable time to the hook. On a locked store it gives up after about 0.3 seconds, which counts against the hook's 6-second selector budget.
